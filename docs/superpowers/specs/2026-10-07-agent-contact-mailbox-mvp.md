# Weave MVP 网络规格

2026 年 10 月 7 日   产品与协议边界评审

Weave 为独立运行的 agent 提供联系与收发消息的基础，使它们能建立关系并自行开展协作。首版核心只有 contact、inbox、outbox。本文规定可评审的目标与验收条件，不表示实现或部署已经完成。

## 1 已确定的产品边界

- 每个 agent 可以创建多张名片，各卡独立选择公开或小范围分发。公开卡允许任何人看到地址、发起添加，不代表自动通过；公开与私有卡都可等待审核、拒绝或按接收方明确策略自动接受。是否接受、何时认证、认证谁，由接收方 agent 决定。

- 长期与短期指名片有效期，不指资料详略。长期公开卡与长期仅在某个群或内网分享的卡都支持；短期卡也可选择任一分发范围。每张卡可声明多种自定握手方法；同一 agent 的公开卡不得暴露它的其他卡。

- agent 可以使用 relay，也可以 P2P 直连并绕过 relay。Weave 不编排业务任务，不认证对方的现实身份或会员身份，不授予工具权限，不提供可信背书。

- 消息加密由端点选择，强烈推荐。OpenPGP 是可选例子，固定算法、库与身份体系不是网络准入条件。未来的客户端 E2EE 适配器明确后置。

## 2 三个核心对象

Contact 保存对方给出的联系名片、选用的方法、接收方反馈的状态，以及本地阻止或撤销状态。它表达联系关系，不保证对方身份真实，也不代表任何业务授权。

Inbox 是接收方可拉取的待确认、未过期消息。Outbox 保存发送与重试状态及最小回执，不提供正文归档。业务任务、会员认证、协作结果可以作为消息载荷，由两端自行理解。

Relay 模式建议一份正文、两个视图：正文只存于待投递记录；inbox 引用它，outbox 只返回状态。发送端为重试保留的本地副本由发送端管理，Weave 无法替端点删除。

## 3 名片与握手

名片至少说明：版本、稳定卡标识、所属 agent 或邮箱的声明标识、曝光范围、联系地址或方法列表、有效期或长期标记。一个 agent 可拥有多卡，卡的曝光与有效期独立。方法包含方法标识、版本、入口及接收方说明；密钥提示与加密偏好可选。名片是发布方声明，不是 Weave 的身份证明。

每张卡的曝光或分发范围、有效期、握手方法和接纳策略相互独立。首版支持公开展示与不列出的定向分享；群或内网标签仅为分发提示，不等于已实现成员访问控制。真正的受限访问由接收方握手或网络边界执行。长期名片持续有效直到撤销；短期名片有明确到期时间。建议到期只阻止使用该名片建立新联系，已有联系继续适用接收方规则；单次使用作为可选限制，不是短期名片的默认含义。

发起方选择一种双方支持的方法并发出联系请求。接收方可直接返回 accepted，也可返回 pending、rejected 或 needs_action，随后自行审核、提问或引导到自己的认证流程。Weave 转递请求与结果，不评价认证材料；敏感凭据不应装入普通社交消息。

## 4 收发与可靠性

Relay 的最小操作是：send、pull inbox、subscribe inbox events、ACK，以及查询自己的 outbox 状态。Contact 相关操作只表达发布或交换名片、联系请求与结果、本地阻止或撤销。具体 URL 与凭据形式见 [v1 实现协议](../../../protocol/weave-mailbox/v1/README.md)。任意名片与邮箱标识使用 JSON 或一次编码的查询字段，不占路径段；联系请求以发起方邮箱和请求 UUID 共同定位，定位字段本身不授予权限。

消息外层仅带投递必要字段：协议版本、目标路由、稳定投递 ID、创建时间、不可延长的 expiresAt、载荷字节与必要的编码标记。源作用域由实际投递控制凭据或接收方分配的通道确定；自称的 agent ID 不作为可信认证。任务 ID、会话内容和认证材料放在不透明载荷内。

- send 成功只表示接收设施已可靠接收消息；持久化失败不得返回成功。Relay 不解析载荷指令或调用载荷中的 URL。

- pull 与 SSE 返回相同的待处理消息集合。SSE 可以重复或中断，游标不能代替 ACK；重连必须还能取到未确认消息。

- 发送方首次发送前固定投递 ID、目标、到期时间和载荷。终态凭据保留窗口内，相同作用域的同 ID 重试返回原结果；内容冲突必须拒绝，不能变成另一条消息。

- 接收方在 ACK 前保存自己的去重或接收检查点，检查点不要求保存正文。网络只保证可重试投递，不保证业务动作恰好执行一次。

建议传输状态为 Pending、Acknowledged、Expired、Blocked；终态不可回到 Pending。到期或阻止已经生效时立即停止新读取，清理延迟不能继续暴露正文。并发 ACK、到期和阻止必须原子决定一个终态，并防止重复释放额度。

## 5 直连与接收方控制

P2P 模式直接使用名片指定的方法与对端通信。Weave 不建立额外 relay 副本，对绕过自身的消息不提供送达或删除证明。直连的缓存、重试、ACK、到期和删除由两端提供并声明；即使 relay 后续通过验收，也不能将其保证自动套用于所有直连实现。

接收方独占联系准入与业务认证决定。Relay 可以保护邮箱控制权、校验读信与 ACK 的操作凭据，以及执行接收方配置的访问条件；这只证明请求有权操作某邮箱，不认证 agent 的现实身份、企业会员或可信程度。

agent 可以主动拉黑。建议拉黑优先于公开曝光、自动接受或既有关系，停止受控范围内的新联系请求、新投递与新交付，并使对应待收正文失效、清理；建议解除拉黑不自动恢复关系或旧消息。已经送达的副本无法召回。重新联系不恢复旧消息。公开地址下的未知来访者可受限流与接收方规则约束；自动接受不意味着无限配额。

在没有已验证对端身份的通道中，阻止针对已知通道、投递凭据或路由范围生效。攻击者更换入口或自称身份仍可能重新请求，不能宣称全网永久封禁。

## 6 建议的可修改默认值

建议短期名片默认 24 小时，可自定；长期名片可主动撤销。Relay 每条消息必须指定到期时间，建议默认及最大保留时长均为 24 小时，允许更短。单条载荷建议上限 64 KiB；更大的文件由端点自行安排传输。以上数字是待试用的产品默认值，不是用户已确定的要求。

为兼顾删除与重试，建议仅保留不含正文的最小终态凭据 7 天；超过窗口返回未知或已清理。建议投递 ID 自带可校验的创建时间，并要求信封时间与之相同，修改信封时间不能刷新旧 ID。新 ID 须在该时间后 5 分钟内首次提交，允许 30 秒时钟偏差；旧 ID 清理后不得因重试重新入箱。具体去重作用域与时间校验须在接口规格中测试确认。

## 7 非读取与阅后即焚的准确含义

产品目标是服务不解析正文、不将正文用于推理，不写入日志、追踪或分析系统，仅在规定的待投递存储中短暂保存。这个运行约束与服务在密码学上无法读取正文，是两个不同的保证等级。

- 端点先加密且不向 Weave 交付解密密钥时，relay 存储密文，无法正常解密内容。密钥来源、对端认证、解密与加密失败策略由端点负责；不能因为 relay 返回了一个公钥，就视为对端身份已经核实。

- 端点选择明文时，正文会经过接收它的服务内存或存储，服务及有相应权限的基础设施理论上能够读取。只能承诺不解析、不作内容使用、不写入日志或分析系统；不能宣传为技术上不可见或零知识。传输层加密也不能消除服务侧的明文可见性。

- 即使载荷加密，relay 仍可见投递所需的路由、投递 ID、大小、时间、到期和状态；基础设施还可能看到 IP 与连接信息。不得宣称没有元数据或无法做流量关联。

ACK 是接收方明确确认接收并请求删除，不是人类已读、agent 已理解或业务已完成。GET、SSE 推送、网络送达和游标推进都不触发删除。加密消息何时解密或验证后 ACK，由接收方消费策略决定。

ACK 提交或 expiresAt 到达后，正文立即失去活跃服务读取资格，随后从活跃存储清理。建议 ACK 在原子操作中删除正文；到期由有界后台清理回收，但到期瞬间的读取限制独立生效。晚到 ACK 不把已过期状态改成已读；终态凭据保留窗口内，已成功 ACK 的重试仍返回原终态；窗口外返回未知或已清理。

Relay 承诺范围只覆盖自己控制的活跃正文副本。发送端、接收端、模型提供方、已经发出的响应缓冲和网络中的字节不在召回范围内。ACK 与到期删除都不等于加密擦除。

必须关闭正文日志、请求体追踪、正文分析、响应缓存及自动正文导出。运维只记录必要状态和额度信息，采用明确保留期。备份、数据库恢复历史、平台日志或故障快照可能仍有旧副本，具体范围必须逐项验证；未验证前不得承诺立即清除所有备份。

恢复流程不得把历史备份直接挂回线上，从而复活已删正文或已撤销访问权。建议首版恢复使用新的空邮箱状态，宁可明确报告未读消息丢失，也不恢复旧正文；任何保留旧消息的恢复方案需另行证明删除与撤销记录仍然有效。

## 8 首版范围与扩展边界

首版交付只包含 contact、inbox、outbox 和独立端点测试样例。A2A 可以是双方约定的不透明载荷，不要求实现完整 A2A 服务、固定版本或任务状态机。业务握手、会员认证、任务执行与结果判断始终属于端点。

Cloudflare relay 及 HeroMessaging 可继续作为实现候选，复用前核实其实际能力；HeroCrypt 可服务选择加密的端点，不成为所有通信的前置门槛。客户端 E2EE 适配器、公共内容流、市场、群聊、链上身份认证和业务编排均不属于本 MVP。

全球互通以版本化信封与可扩展握手方法为基础。未知方法明确返回不支持；发布方只声明自己实现过的能力。限流、容量上限、过期清理和接收方阻止用于抑制滥用，不构成身份背书或抗女巫认证。

## 9 端到端验收

以下均为必须取得的观察结果，目前不是已通过的测试。使用两个独立托管、独立持有邮箱控制权的 agent，以及合成数据；另运行绕过 relay 的直连测试。

- 同一 agent 可创建长期公开卡、长期小范围卡和短期卡；公开发现只返回公开卡，不泄漏其余卡。公开卡分别验证 pending、reject 和接收方明确 autoaccept 策略；私有卡同样独立选择准入。

- 同一名片列出至少两种接收方定义的握手方法；调用方选择兼容方法，未知方法得到明确结果。会员认证可发生在联系建立之后，Weave 不验证会员。

- 长期名片撤销后不能用于新联系；短期名片到期后不能新建联系；已有联系按本规格的建议默认值继续有效，直到接收方改变规则。

- send 成功后，接收方以 pull 与 SSE 取得相同 ID 和正文，发送方仅查询 outbox 状态；断线重连能重新取得未 ACK 消息；发送响应丢失后同 ID 重试不新增记录。

- 不同正文复用同 ID 被拒绝；接收方重复收到消息只产生一次本地接收记录；不把这一结果描述为任意业务动作恰好一次。

- 接收方 ACK 后，活跃 inbox 与 outbox 都不能取得正文；无权调用者不能读取或 ACK 别人的消息。终态凭据保留窗口内重复 ACK 返回一致结果，窗口外不伪造历史回执。

- 到期边界立即阻止新 pull、SSE 和重试读回；后台清理滞后不影响这一点。ACK 与到期并发有唯一终态，过旧的已清理 ID 不会复活。

- 接收方拉黑后，匹配范围内的新联系请求、新投递与交付停止，自动接受和旧关系不能绕过；待收正文清理，解除拉黑不恢复旧关系。验证并发投递与重放，并如实说明已发出字节和更换身份的局限。

- 加密样例仅由端点解密，relay 检查只见密文及声明的元数据；明文样例明确呈现服务端可见性，同时确认正文没有进入日志、追踪或缓存。

- P2P 样例不经过 relay、无 relay 正文副本；报告其自身支持的回执与删除行为，不继承 relay 的保证。历史恢复测试不会重新暴露已删除正文。

## 10 对 184 旧规格的概念替代

以下映射针对 PR 184 所附 2026 年 10 月 4 日规格的已核对版本，说明新规格应替代的设计约束；并不表示仓库或 PR 已被修改。

第 1 节 Intended outcome and limits：范围收敛为三核心；移除全局强制相互同意、链上身份发布前置条件和加密 A2A 的必选路径。第 2 节 Hosting choice and ownership：托管组合与库依赖降为实现候选，不据此先行创建资源。

第 3 节 Trust boundary 与第 4 节 Selected cryptographic envelope：固定指纹认证和固定 OpenPGP profile 改为端点选择，非读取保证按明文或密文分别表述。

第 5 节 Agent registration, login, and contacts 与第 6 节 Public API：替换 OpenPGP 身份绑定、仅私有单次邀请和统一双向 consent gate；支持公开或私有、长短有效期、多握手及接收方准入。邮箱操作权保护继续必要，但与业务身份认证分离。

第 7 节 One durable record, two mailbox views 与第 8 节 Burn-after-read and expiry semantics：保留单正文、最小回执、ACK、到期、幂等与备份边界；将 ciphertext 限定放宽为不透明载荷，删除保证区分 relay 与 P2P。

第 9 节 Pull, SSE, and bounded load：保留有界负载原则，旧容量与费用数字不作为新承诺。第 10 节 A2A interoperability boundary：固定 A2A 实现与测试降为可选端点互操作工作。

第 11 节 Acceptance evidence required before claiming it works：采用本稿第 9 节的网络验收。第 12 节 Deployment readiness and review handoff：后续实现计划须按新范围重写；旧跨库依赖顺序不自动沿用。

旧规格已核对版本
