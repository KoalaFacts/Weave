# Demo Agent Start and non-secret invitations

## Delivered scope

The Worker homepage exposes `/agent-start.md` in server-rendered HTML before account setup. The optional stdio MCP reads the same checked-in guide and returns it through `demo_guide.instructions`, alongside safe readiness metadata. Its former linear `steps` list is replaced by the canonical state-based instructions. Existing tool schemas, HTTP mailbox operations, recipient authority, credential rules and retention remain unchanged.

The rendered A/B copy prompts point to that guide instead of independently prescribing fixed ping/pong text. The original browser walkthrough remains a manual example, not the agent execution contract.

The contact-card panel reads only the current account's existing addresses. It emits an allowlisted non-secret invitation with origin, recipient IDs and an explicit test runId. Preparation and copying never register, publish, request, accept or send. Copies/rebuilds preserve the same run unless the user explicitly starts another test or selects a different address. Changing selection invalidates the previous card immediately; copying also validates selection and current address effectiveness. Clearing/switching accounts invalidates the panel and stale reads. No persistent browser storage was added.

Contact request metadata is body-free. The guide explicitly requires recipient inbox pagination and introduction matching by requester, recipient and requestMessageId before review/acceptance. Missing, malformed or mismatched introductions do not authorize automatic acceptance.

Client state names and runId/replyTo are reporting/application-text conventions, not new HTTP request fields or a workflow API. Hosts must retain real checkpoints/envelopes and supply receiving execution. This increment does not implement hosted-agent wake, an autonomous loop, a durable client store, E2EE, or independent reasoning-agent acceptance testing.

## Release path

The existing manual `Deploy Weave Worker` workflow remains available with repository/production configuration scopes. An explicit push of an already-merged commit to `publish/demo` supplies a git-based release signal using the existing repository configuration; normal main pushes do not deploy. The verify job checks that the selected SHA is checked out and is an ancestor of main before the existing Worker tests, audit and C# compatibility checks. No branch force-update is needed or authorized by this change.

Both deployment jobs still use the existing resource-inspecting deployment script, retain the production environment gate where applicable, and then make anonymous read-only requests to the fixed demo origin. The published guide must exactly match the checked-out source; the homepage must expose the agent entry and invitation controls. Failure is reported as verification failure, not silently retried or called success. No account/message is created on the public demo by this verification.

## Toolchain and security prerequisite discovered in CI

Floating SDK installation selected 10.0.402 while the committed implicit ILLink dependency graph expected 10.0.12, causing NU1004 before security auditing. Selecting the previously verified SDK 10.0.401 exposed the next real failure: System.Security.Cryptography.Pkcs 9.0.18 had newly reported advisories. The initial repair used SDK 10.0.402 with exact selection, installed it through global.json, and centrally pinned the existing transitive PKCS dependency to the vendor-patched 9.0.21. This does not add SQL/provider dependencies to consumers that did not already use them.

The lockfiles were regenerated by NuGet on an isolated repair branch, not fabricated or hand-edited. The normal strict locked dependency audit passed on that regenerated graph in Actions run 38490594786. The one-use regeneration workflow removed itself before its generated commit; it is not retained as a main-branch workflow. Audit thresholds, lock enforcement in verification, browser sandboxing and normal checks were not weakened. Future SDK servicing changes must deliberately regenerate and verify the corresponding locked graph.

Vendor advisory: https://github.com/dotnet/announcements/issues/468 (published 2026-10-13; PKCS 9.0.21 and SDK 10.0.402 are the patched versions used here).

## Subsequent SDK selection policy

The owner subsequently chose compatibility across the stable .NET 10 major version. `global.json` now uses `10.0.100` with `latestMinor` rather than an invalid wildcard or an exact servicing pin; CI installs `10.x` and retains `dotnet-quality: ga`. The earlier exact-SDK repair and Actions evidence above describe that earlier revision. The central PKCS security fix, strict NuGet auditing and locked restore remain required. SDK selection alone is not proof that a changed implicit dependency graph matches the committed locks.

The current ILLink and Dashboard static-web-assets build packages remain at `10.0.13` through explicit private package references and central version management. This separates the current locked package graph from the SDK's implicit servicing versions, allowing SDK `10.0.401` to restore that graph without downgrading the PKCS security fix. ILLink is referenced for the existing trimmable/AOT-compatible projects; the assets package is referenced only by Dashboard. Normal NuGet restore preserved the committed lockfiles without version or hash changes. Future SDK or publish-mode changes still require locked restore, build and applicable runtime/browser verification; this does not guarantee compatibility with every future .NET 10 SDK.
