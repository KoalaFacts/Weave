# Native Worker and D1 mailbox demo

Local implementation based on `b53fa3005d317b1205c748bc860be0c7b856d05c`; no cloud resource, remote migration, deployment, package publication or production credential change was performed. The existing C# host and SQLite provider remain separate. This is not a migration of their stored mailboxes.

## Delivered path

[`hosts/Weave.Mailbox.Worker`](../../hosts/Weave.Mailbox.Worker/README.md) contains a native TypeScript `fetch` Worker, D1 migration, local runtime tests and a browser entry at `/`. Registration returns `agentId` with an optional private profile and zero initial addresses. Each agent can create multiple addresses backed by the existing card records. Public discovery includes only public, currently effective addresses; private profiles and address counts are not joined into public results. The owner manages addresses using the mailbox control header. Direct HTTP(S) URIs are stored metadata only.

Contact admission, decisions, generation fences, envelopes, ACK, receipts, pull and bounded SSE preserve the existing v1 wire shapes. `/inbox/{agentId}` and `/outbox/{agentId}` bind the path to the authenticated identity. D1 revision-guarded batches protect concurrent updates; local process-restart tests exercise durable decisions, receipts, counters and ACK tombstones. These tests do not establish remote Cloudflare durability or performance.

The control verifier uses `node:crypto` SHA-256 and native `timingSafeEqual` on equal-length decoded digests. The immutable scheme and explicit parameters are stored with the digest. The application requires at least 64 characters without introducing a custom alphabet or maximum; the UI generates 32 CSPRNG bytes as hex. Length does not prove entropy. Recovery keys and private keys are not implemented. See the host README for the full hash, transport, retention and quota contracts.

The browser entry supports two-agent registration, addresses, directory browsing, contact decisions, messages, ACK and SSE. It keeps control material in memory, uses a fresh CSP nonce and does not fetch direct URIs. An uncertain submission retains its original envelope; a confirmed submission followed by a failed list refresh is not offered as a resend. Asynchronous actions capture their account session and cannot dispatch under a later account.

## Browser failure baseline

A separate clean worktree at `b53fa3005d317b1205c748bc860be0c7b856d05c` passed locked solution restore and complete Release build, then reproduced the same five failures by running the original xUnit executable with `-class Weave.Silo.Tests.Dashboard.DashboardReviewBrowserTests`. It ran five tests, all failed, none skipped. The tests and Dashboard implementation are unchanged in this contribution. This supports an environment blocker rather than a Worker regression; it does not mark the gate passed.

All five fail before browser debugging becomes ready with the same Chromium error:

```text
The SUID sandbox helper binary was found, but is not configured correctly. Rather than run without sandboxing I'm aborting now. You need to make sure that /usr/lib/chromium/chrome-sandbox is owned by root and has mode 4755.
```

Affected methods in `Weave.Silo.Tests.Dashboard.DashboardReviewBrowserTests`:

- `Review_ClearWhileVerifying_CancelsUpstreamAndDiscardsRetainedInput`
- `Review_UpstreamDeniesReview_ShowsSafeDenialWithoutVerifiedContent`
- `Review_InvalidUpload_RejectsBeforeContactingUpstream(oversized: False)`
- `Review_InvalidUpload_RejectsBeforeContactingUpstream(oversized: True)`
- `Review_UploadAndVerify_RendersExactContentAndInvalidatesWhenWorkspaceChanges`

Local Wrangler migration was also applied a second time: it reported no pending migration, retained identical mailbox row hashes and SQLite sequence state, and kept one `d1_migrations` record. Only the initial version exists; a future version upgrade is not yet tested. Remote resource creation and migrations were not performed.

A follow-up review reproduced address-editor state surviving Clear session/account switching. The shared reset now clears label, validity bounds, direct URI, edit identity and public checkbox using the same helper as Cancel edit. Two original-page-script regressions failed before the fix and verify both transitions and the next account's empty/private creation payload afterward. These remain simulated-DOM tests, not browser E2E.

SSE tail starvation was reproduced with 9 and 64 pending messages. The final fix keeps one fresh D1 snapshot per event and persists a server-owned traversal position across finite connections. Independent version CAS prevents late concurrent releases from rewinding it; a completed traversal wraps and replays unacknowledged messages. This differs from the C# host's longer traversal scheduling but does not turn any cursor into ACK. Real workerd reconnect tests visit and revisit every pending message without ACK; controlled writes against real D1 verify ACK/block between events and stale-release isolation. The 48-query cap remains enforced. Browser E2E remains unverified.

The demo now derives new relay endpoints from the actual request URL origin by default, ignoring Forwarded/X-Forwarded-Host. No host variable is mandatory. Optional WEAVE_HOST overrides must pass origin validation. Runtime configuration targets the user's existing Worker name demo; database ID is still a placeholder and no remote configuration or deployment was performed. Three reported unused imports were removed.

The D1 binding is consistently lowercase `db`, matching the operator's existing binding. Runtime access is `env.db`; Wrangler and all fixtures use that name without an uppercase alias. The checked-in database ID remains a placeholder; the deployment workflow reads the actual name/ID from the selected existing GitHub configuration scope.

## Manual deployment workflow follow-up

The manual `deploy-weave-worker.yml` supports repository configuration and the existing `production` environment. It accepts only main, serializes deployment runs, verifies the Worker and C# wire contract before credential use, and never runs on pushes or pull requests. The deployment script checks the existing `demo`/`db`/`weave-389` resource identity, then runs numbered migration list → apply → list → explicit no-pending confirmation → deploy. Permission denial, identity mismatch or migration failure stops without resource creation or permission fallback. Current Cloudflare role instructions use Workers Editor scoped to demo plus D1 Edit for migrations. See the host README for configuration names and rerun semantics. This is an implementation and local-verification result, not evidence of remote deployment.

The exact original full-suite command was `dotnet test --solution Weave.slnx --no-build -c Release`. The clean baseline reproduction used:

```sh
source /workspace/weave-toolchain/env.sh
dotnet restore Weave.slnx --locked-mode
dotnet build Weave.slnx --no-restore -c Release
python3 /workspace/weave-toolchain/reap.py dotnet tests/Weave.Silo.Tests/bin/Release/net10.0/Weave.Silo.Tests.dll -class Weave.Silo.Tests.Dashboard.DashboardReviewBrowserTests
```

The reaper only owns/reaps child processes; it does not filter tests or change browser flags. All five failures occur in fixture startup before browser/product actions. The outer child-process assertion reports Chromium's startup failure, not a failed product behavior assertion. No sandbox bypass was used.
