# Demo registry, MCP and cleanup security verification

This record describes application checks on the Worker demo, not a formal compliance certification, penetration test or assertion that the public deployment is secure. It extends the [Worker implementation record](2026-10-12-worker-d1-demo.md). The existing .NET Chromium startup failures and remote-deployment gates remain unresolved.

## Delivered boundaries

The anonymous `/registry` page uses the existing public directory projection. The native Node [demo MCP](../../examples/mailbox-demo-mcp/README.md) exposes concrete tools over the same HTTP endpoints; it does not gain direct D1 access or create an alternative authorization path. Startup/discovery never registers a remote account. Account control is an operator-supplied environment value; tests use separate local synthetic controls. The scheduled handler has no public HTTP maintenance route.

## Cleanup policy and residual limits

The existing v1 retention rule is seven days for terminal body-free receipts, with UUIDv7-bound creation time and a five-minute first-admission window. No new retention exception was introduced. Every scheduled round counts distinct selected message rows, not SQL statements; each row can be body-cleared and purged in the same atomic batch without counting twice. The configurable cap cannot exceed100000, while the current D1 implementation processes at most64 per batch/two batches per scheduled invocation (default128). The default two-second monotonic budget stops admission of further work; already-started transactions can finish. An eligibility scan ordered by sequence resumes unfinished records without a permanently advancing cursor. Contact cleanup retains its separate128-request bound and updates matching channel references in the same transaction.

The initial schedule is every five minutes; no guarantee is made that a backlog clears in five minutes. No real remote cleanup was executed. Deployment of the Cron Trigger would activate body clearing and eventual seven-day receipt/request deletion on the configured database; that scope must be included in deployment authorization. Logical deletion does not prove backup/media erasure. No full-table body materialization or100k-message transaction was added. The current model caps stored messages at8000; there is no100k-scale performance claim.

## Verification limits and promotion gate

Local dependency audit, staged credential scan, YAML parsing, typechecking, actual Worker tests and the C# source-generated wire harness complement these tests; audit zero alone does not establish security. Independent review verified both MCP fixes and inspected registry output, rate-limit SQL and cleanup bounds/retention. No production credentials were generated, committed or printed, and no remote account, migration, deployment or deletion was performed.

Remote Cloudflare behavior, account-level deployment-read permissions, real ingress headers, plan cost/quota/performance, scheduler delivery and graphical browser E2E remain unverified. Prior full .NET result remains4252passed/13skipped/5failed; the same five fail during Chromium startup on clean baseline. Do not merge or describe all CI as green on the strength of these local checks. The user has not granted a new coverage exception.
