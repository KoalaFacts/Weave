# Demo registry, MCP and cleanup security verification

This record describes application checks on the Worker demo, not a formal compliance certification, penetration test or assertion that the public deployment is secure. It extends the [Worker implementation record](2026-10-12-worker-d1-demo.md). The .NET Chromium startup failures below describe the earlier local environment. Current Worker UI evidence comes from the separate [Worker verification workflow](../../.github/workflows/worker-browser.yml), whose protected-browser result and screenshots must be checked for the reviewed commit. Remote-deployment permissions remain a separate gate.

## Delivered boundaries

The anonymous `/registry` page uses the existing public directory projection. The native Node [demo MCP](../../examples/mailbox-demo-mcp/README.md) exposes concrete tools over the same HTTP endpoints; it does not gain direct D1 access or create an alternative authorization path. Startup/discovery never registers a remote account. Account control is an operator-supplied environment value; tests use separate local synthetic controls. The scheduled handler has no public HTTP maintenance route.

## Cleanup policy and residual limits

The demo now pins `CLEANUP_MAX_MESSAGES=0` and `CLEANUP_TIME_BUDGET_MS=0` in both checked-in configuration and deployment code, ignoring inherited environment values. Scheduled and opportunistic business sweeps do not start database work. A real local D1 regression preserves expired messages, contact requests and channel references while public-rate housekeeping continues. Temporary counter, lease and guard cleanup remains independent; ACK, blocking and existing terminal-message handling can still clear bodies. The following limits describe the runtime engine when explicitly enabled, not this disabled demo profile.

The existing v1 retention rule is seven days for terminal body-free receipts, with UUIDv7-bound creation time and a five-minute first-admission window. No new retention exception was introduced. Every scheduled round counts distinct selected message rows, not SQL statements; each row can be body-cleared and purged in the same atomic batch without counting twice. The configurable cap cannot exceed100000, while the current D1 implementation processes at most64 per batch/two batches per scheduled invocation (128 messages). When bindings are absent, the runtime falls back to 128 messages and a two-second monotonic budget; the demo supplies explicit zeros. An enabled monotonic budget stops admission of further work; already-started transactions can finish. An eligibility scan ordered by sequence resumes unfinished records without a permanently advancing cursor. Contact cleanup retains its separate128-request bound and updates matching channel references in the same transaction.

The Cron Trigger remains every five minutes, but deploying the pinned demo configuration does not enable its business sweeps. The deployment script reads the actual Worker settings afterward and requires both cleanup bindings to be plain-text zero; a failed check reports that deployment already completed and stops without retry or rollback. Enabling sweeps requires a reviewed source/configuration change and authorization for body clearing and eventual seven-day receipt/request deletion. Even when enabled, there is no guarantee that a backlog clears in five minutes. No real remote cleanup was executed for these local checks. Logical deletion does not prove backup/media erasure. No full-table body materialization or100k-message transaction was added. The current model caps stored messages at8000; there is no100k-scale performance claim.

## Verification limits and promotion gate

Local dependency audit, staged credential scan, YAML parsing, typechecking, actual Worker tests and the C# source-generated wire harness complement these tests; audit zero alone does not establish security. Independent review verified both MCP fixes and inspected registry output, rate-limit SQL and cleanup bounds/retention. No production credentials were generated, committed or printed, and no remote account, migration, deployment or deletion was performed.

Remote Cloudflare behavior, account-level deployment-read permissions, real ingress headers, plan cost/quota/performance and scheduler delivery remain unverified by these local checks. The historical full local .NET result was 4252 passed / 13 skipped / 5 failed; those five failed during Chromium startup on the clean baseline too. That result does not replace current complete CI or the separate real Worker browser regression. Inspect its screenshots before claiming visual acceptance. No coverage exception is introduced.
